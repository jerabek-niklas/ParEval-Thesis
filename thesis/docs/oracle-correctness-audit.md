# Oracle Correctness Audit

Audit of the mathematics- and convention-sensitive ParEval benchmarks (issue #57). Question answered here — deliberately **not** the one the earlier example-consistency check answered:

> The example check proves `documented example == oracle output`. It does **not** prove that the oracle implements the operation the benchmark name and prompt claim. This audit tests the second statement.

Analysis only. No fix implemented, no open project or policy decision taken; where several legitimate resolutions exist, the options and their trade-offs are reported and the decision is left open. Date: 2026-08-24.

## Executive Summary

- **22 newly audited** benchmarks, **1 previously calibrated reference** (`sparse_la/45_sparse_la_sparse_solve`, not re-run), **23 covered in total**.
- **Correct (primary class A): 6** — `01_dense_la_solve`, `02_dense_la_gemm`, `04_dense_la_gemv`, `19_graph_shortest_path`, `51_stencil_edge_kernel`, `54_stencil_game_of_life`. In each case the oracle was shown by execution to sit exactly on the convention the prompt pins, against an independent ground truth.
- **Ambiguous (primary class B): 8** — the oracle implements a plausible common convention that the prompt does not pin.
- **Confirmed oracle bugs (class C): 0.** No oracle in this scope was shown to implement the wrong operation. This is a substantive negative result: the `fft/07` failure mode — an oracle matching *none* of the plausible conventions — has no counterpart among these 22.
- **Domain mismatches (primary class D): 2** (`24_histogram_count_quartile`, `49_sparse_la_sparse_lu_decomp`); 14 further D-class findings at finding level.
- **Validator-equivalence bugs (primary class E): 1** (`40_sort_..._by_magnitude`); 2 at finding level.
- **Other demonstrated inconsistencies (primary class F): 5** (`00_dense_la_lu_decomp`, `11_geometry_convex_hull_perimeter`, `26_reduce_product_of_inverses`, `52_stencil_1d_jacobi`, `53_stencil_2d_jacobi`).
- **Benchmark-design observations** (explicitly *not* oracle-correctness bugs) recorded for 19 of the 22.
- **Blockers before implementation: 21 findings across 12 benchmarks plus 3 family-level findings.** Every one is either a genuine specification ambiguity with several common readings, or a validator that accepts demonstrably wrong answers, or a domain the driver enters but the oracle does not cover.
- **Finding-level tally:** 71 benchmark-level non-A findings (F 33, B 22, D 14, E 2) plus 26 family-level non-A findings (F 20, D 3, B 3).
- **Adversarial verification: 20 findings independently re-derived by separate agents, 20 CONFIRMED, 0 REFUTED**, 2 reclassified (see *Method*). 3 further verification agents died on API errors; those findings carry only their own auditor's falsification attempt. Verification therefore covers the blockers and a sample of the rest, not all 97 findings — a coverage limit, stated rather than hidden.

### Contradictions with the existing consistency check (§3c)

`thesis/docs/benchmark-example-consistency.md` classified all 22 of these benchmarks as `consistent`. **That verdict is not wrong for any of them** — this audit did not find a single benchmark whose documented example fails against its oracle. But the verdict is **insufficient for 16 of the 22**: those carry at least one semantic deviation between prompt, claimed operation, driver, validator or independent ground truth that a matching example provably cannot expose. The sharpest instances:

- `34_scan_largest_contiguous_subarray_sum` — the example's answer is positive, so it cannot discriminate the empty-subarray convention that decides all-negative inputs.
- `40_sort_..._by_magnitude` — the example has no equal magnitudes, so it cannot expose that the validator demands the oracle's unspecified tie order.
- `24_histogram_count_quartile` — the example has no negative values, so it cannot expose that negatives all land in `bins[0]` under no reading of the prompt.
- `46/47/48/49_sparse_la_*` — every documented example is duplicate-free, so none can expose the COO duplicate convention, which the family splits on (46/47/48 sum, 49 and 45 overwrite).
- `11/13/14_geometry_*` — the examples are all non-degenerate, so none can expose the `n < 2` / `n < 3` return values that live enhanced specs actually grade.

That is precisely the defect class this audit exists for, and it is the reason the example check must not be read as a correctness certificate.

## Method

### Files read (per benchmark, by the auditing agents)

For each of the 22: the three prompt entries (`serial`, `omp`, `mpi`) in `thesis/prompts/generation-prompts-thesis.json`; `drivers/cpp/benchmarks/<family>/<name>/baseline.hpp`; the same directory's `cpu.cc` including `validate()` and the input generation; `drivers/cpp/utilities.hpp` (comparison helpers, `fillRand`, constants); `drivers/cpp/enhanced-fill.hpp` where the size/fill override mattered; `drivers/cpp/models/serial-driver.cc` (and `omp`/`mpi` variants where a parallel path was exercised); `drivers/build-configs.json` and `drivers/problem-sizes.json` for the real compile flags and sizes; and `gpu.cu` / `kokkos.cc` of the same benchmark where a family-consistency question required it. Family-consistency agents additionally read the sibling drivers of their family.

**Deliberate read restriction:** the 22 auditing agents were instructed **not** to read anything under `thesis/docs/`. The comparison against the existing consistency check (§3c) was performed afterwards by the orchestrator. Rationale in *Premise check*.

### Independent references

No expected value in this report is taken from a documented example or from a baseline. Every benchmark was given at least one case whose answer is known independently. The reference machinery, by benchmark class:

- **Exact rational arithmetic** (`fractions.Fraction`, host Python, stdlib only): LU/solve/GEMM/GEMV/SpMV/SpMM/axpy/sparse-LU candidates, geometry predicates and areas, quartile bin decisions on exact binary64 values, Kadane candidates in arbitrary-precision integers.
- **Analytically known answers**: 3-4-5 triangle (perimeter 12, closest pair 5), unit square (perimeter 4), integer lattices (closest pair = lattice step), simple path graphs (distance = |i−j|), Game-of-Life still lifes/oscillators/gliders, Pythagorean-triple magnitudes.
- **Independent re-implementations** of every enumerated convention, written from the mathematical definition without consulting `baseline.hpp` — 12 Game-of-Life variants, 10 2-D-Jacobi variants, 12 closest-pair-1D readings, 7 hull output conventions, 7 quartile readings, and so on.
- **Higher precision** where doubles were the confound (50-digit `Decimal` for `sqrt`, `long double` accumulation, exact bit-pattern conversion of every test double).

### Test strategy

Per benchmark: a normal case, at least one **constructed discriminating case**, and the relevant edge/degenerate cases (minimal sizes, duplicates, collinear/coincident inputs, zero/NaN/Inf, extreme magnitudes). The documented example was used only as an additional case. Every convention enumeration had to *prove* it discriminated — the report records, per benchmark, how many candidates were pairwise distinct on the separating input. Symmetric or degenerate inputs that fail to separate were kept in the record as negative controls (e.g. `13_geometry_closest_pair_2d`: a monotone collinear ramp makes "consecutive pairs only" coincide with the true minimum — which is why the asymmetric 5-point set is the decisive one).

The **discarded-ground-truth check** (a driver that builds or trivially knows the true answer and then throws it away, using the baseline as sole truth) was run on all 22. It is present and confirmed in `00`, `01`, `49` and the sparse family, and is the structural reason several of the defects below can exist unnoticed.

### Numerical tolerances

Semantic deviations were separated from rounding by construction: discriminating inputs use small integers, powers of two, or exactly representable values wherever possible, so that the *correct* answer is exact and any deviation is either 0 or large. Where doubles were unavoidable, deviations were only called semantic if they exceeded the plausible rounding scale by orders of magnitude, and the counter-hypothesis "rounding order / conditioning" is recorded per finding. The validators' own tolerances (absolute `1e-3`, `1e-4`, `1e-6` depending on benchmark) are reported where they themselves are the defect (`00`, `26`).

### Verification

Every non-A finding was queued for adversarial verification by a separate agent with the mandate to **refute** it using its own harness and its own reference. 20 completed: **20 CONFIRMED, 0 REFUTED**. Two reclassifications were accepted and are reflected below: `46_sparse_la_spmm`'s out-of-range-index finding moves D → F (the prompt *does* state the index domain, so it is an inconsistency, not a narrower domain), and `11_geometry_convex_hull_perimeter`'s multiplicity finding is F with D equally defensible. Several verifiers attached severity caveats (recorded per blocker). 3 verification agents died on API errors; the affected findings (`52`'s validator-window and size-1/2 findings, `13`'s overflow-sentinel finding) rest on their own auditor's falsification attempt only.

## Calibration reference

**What the `sparse_la/45` calibration established.** Two things. (i) The pre-existing method reliably finds concrete inconsistencies *between* prompt, driver, data representation and oracle — the duplicate-COO conflict, the NaN-blind comparator, the discarded ground truth. (ii) It has a blind spot: an oracle that is internally consistent, crash-free, and matches its own documented example can implement a different operation and still pass as "consistent". `45` is not re-audited or re-run here; it appears only as the family reference point for the duplicate-semantics question.

**How Section 4 addresses the blind spot.** Instead of asking "does the oracle agree with its example", it asks "which of the *common conventions of the claimed operation* does the oracle implement" — enumerate the plausible conventions first, construct an input that separates them, then determine the answer by execution, and only afterwards check whether the prompt pins that convention. An oracle matching no candidate is the signature of the `fft/07` failure mode.

**Self-test of Section 4 on `fft/07_fft_fft_conjugate`** (not in scope, not re-audited; Section 4 applied only, and *before* consulting `thesis/docs/fft-family-consistency.md`):

1. Claimed operation, from name + prompt: "compute the Fourier transform of x in-place, return the complex conjugate of each value" — i.e. `conj(DFT(x))`.
2. Conventions enumerated: exponent sign `{−1, +1}` × normalisation `{none, 1/N, 1/√N}` × final conjugation `{no, yes}` = **12 candidates**, each implemented independently in Python from the definition.
3. Discriminating inputs: a complex asymmetric sequence `x[n] = (0.3 + 0.7n) + i(−0.5 + 0.2n²)`, plus a real asymmetric control. The discrimination check confirms the calibration warning quantitatively: on the complex input **all 12 candidates are pairwise distinct at N ≥ 4**, on the real input only **6 of 12** are — a real-valued example cannot decide this question at all.
4. Oracle (`fftCooleyTookey`, the function `cpu.cc` actually calls for validation), by execution:

   | N | candidates matching the oracle | best residual error |
   |---|---|---|
   | 2 | `exp±/unnorm/conj` (sign degenerate at N=2) | 1.1e-16 |
   | 4 | `exp+/unnorm/noconj` — a real convention, but not the claimed one | 1.8e-15 |
   | 8 | **none of the 12** | 15.5 |
   | 16 | **none of the 12** | 117 |

**Result: the self-test reproduces the known defect.** Section 4 returns "matches no enumerated convention" at N ≥ 8, exactly as predicted, so the step is strong enough to be relied on for the 22. (Comparison with `fft-family-consistency.md`, performed only afterwards, agrees.) The corresponding limitation is stated in *Premise check*: the step's power depends on the enumeration being rich enough, and "no separating input found" was treated as a blind spot rather than a pass throughout.

## Benchmark-design observations

These are **not** oracle-correctness bugs: in each case the prompt does not demand the affected method, other correct implementations exist, and the mathematical task remains correctly specified. They are recorded because they bear on what the benchmarks can measure.

**Validation does not exercise what the benchmark times.** `02_dense_la_gemm` and `04_dense_la_gemv` validate only square shapes (`M=K=N`) while the timed region runs genuinely non-square shapes — a dimension- or stride-confused submission passes validation and, in `04`, gains a measured ~3× "speedup" by touching half the data. `46_sparse_la_spmm` has the same square-only validation against a timed `M=256, K=64, N=128`.

**Validation windows that inspect nothing.** The stencil family's interior-only loop (`for i in 1..TEST_SIZE-2`) means `52`, `53` and `54` never check boundary cells — so `52`'s and `53`'s explicitly stated zero-padding rule is unenforceable, and at `TEST_SIZE ≤ 2` the loop body never executes (7 of `52`'s 20 realised specs, 11 of `54`'s 17 gated specs compare 0 or 1 cells). `48_sparse_la_sparse_axpy`'s entire enhanced spec set is vacuous: all 20 specs have `size ≤ 8`, where `nVals = floor(size·SPARSE_LA_SPARSITY) = 0`.

**Absolute tolerances against scale-dependent answers.** `12_geometry_smallest_triangle` compares with an absolute `1e-4` while the correct answer *shrinks* with n (measured over 30 draws at the driver's own n=1024); `14_geometry_closest_pair_1d` has the same shape of problem; `26_reduce_product_of_inverses` compares with `1e-4` a result whose magnitude spans ~1e-40…1e+40. `00_dense_la_lu_decomp`'s `1e-3` is the extreme case and is reported as a blocker rather than a design note, because it makes a demonstrably correct submission fail.

**Perf paths outside the representable range.** `26_reduce_product_of_inverses` is assigned `DRIVER_PROBLEM_SIZE=(1<<23)`; measured, the oracle's value there is `+inf` (at `1<<20` it is 1.31e+165). Both `compute()` and `best()` time an overflow.

**Reference implementations in the timing path.** `34_scan_largest_contiguous_subarray_sum`'s `best()` calls the O(n²) brute force while the natural correct solution is O(n) — harmless at the thesis pipeline's `1<<8`, misleading at upstream's `1<<20`. `46_sparse_la_spmm`'s oracle is O(|A|·|X|) where any natural sparse implementation is far cheaper.

**Naming pull toward the wrong convention.** `53_stencil_2d_jacobi_5-point_stencil`: in numerical analysis a "5-point Jacobi stencil" almost always means the Laplace relaxation `(N+S+E+W)/4` with the centre *excluded*; this benchmark's operation includes the centre and divides by 5. The prompt states the formula, so the oracle is right and the name is the hazard. `24_histogram_count_quartile`: name and function name evoke statistical quartiles; the operation is a quartering of the unit interval applied to fractional parts.

**Generator artefacts.** `46_sparse_la_spmm`'s `reset()` appends instead of assigns, so the timed input is half zero-padding and grows on every reset (~2.25× more nonzeros, ~4.6× more oracle work). `19_graph_shortest_path`'s driver never zeroes the adjacency matrix between generations — the only graph driver in its family that does not. `40_sort_...`'s `baseline.hpp` uses `std::sort` while including only `<complex>` and `<vector>`; it compiles only because every including translation unit pulls in `<algorithm>` first.

**Structural coupling.** `51_stencil_edge_kernel`'s oracle takes its kernel constant from the model-authored file — the only benchmark in its family that does — so a submission that renames or reshapes `edgeKernel` changes the oracle it is graded against.

## Follow-up candidates

Out of scope; recorded, **not** audited. No further benchmarks were audited on the strength of these.

1. **Suite-wide NaN acceptance in the shared comparators.** `reportAndCompare`, `reportAndCompareScalar` and `fequal` in `drivers/cpp/utilities.hpp` all use `abs(a−b) > eps`, which is false whenever either side is NaN. Every benchmark whose oracle can produce NaN or Inf inherits it. This is the one permitted blast-radius determination (§9 exception): it is a shared utility, and it is the mechanism behind blockers in `26`, `49` and `12`. A cheap suite-wide sweep would be "which oracles can produce non-finite output on their own driver's inputs".
2. **The `n < 2` / `n < 3` gap is probably suite-wide**, not specific to the geometry benchmarks: `stages.enhanced_tests.static_base_sizes = [0, 1, 2, 7]` is applied to every parameterisable benchmark, so any benchmark whose prompt does not state a minimum size gets graded on an oracle-invented value at sizes 0 and 1.
3. **`fillRand`'s integral branch is `rand() % (max - min) + min`** — the upper bound is *exclusive*. Every benchmark documented as filling `[lo, hi]` actually draws `[lo, hi−1]`. Harmless for most, but it is why `49`'s validation always leaves the last row and column of A empty.
4. **The `DBL_MAX`-sentinel-with-strict-`<` idiom** appears across several baselines (confirmed by execution in `13` and `14`, suspected elsewhere): when every candidate value overflows, the sentinel itself is returned as if it were a result.
5. **The interior-only validation loop** is shared by the stencil family beyond the members audited here.
6. **`gpu.cu` / `kokkos.cc` divergences** were observed in several benchmarks (different RNG call order, hard-coded `TEST_SIZE`, `fequal` instead of `reportAndCompare`, non-negative-only fills in `02`'s GPU path, a possibly non-compiling CUDA path in `51`). These paths are dead in this thesis (the prompt file holds only serial/omp/mpi) and were not audited.
7. **`16_graph_largest_component` and `18_graph_count_components`** generate Erdős–Rényi graphs with the same density parameter that makes `19`'s shortest-path distances almost always 1 or 2 — worth checking whether their measurements are similarly degenerate.
8. **The histogram family's `val - (int) val` fractional-part idiom** may be copy-pasted; any sibling casting a double to `int` inherits `24`'s undefined behaviour above 2³¹ and its negative-value asymmetry.

## Premise check

**Premises of the briefing that did not hold.**

1. **"The names below may be inaccurate."** They were not. All 22 resolve exactly against `drivers/cpp/benchmarks/` — `51_stencil_edge_kernel`, `52_stencil_1d_jacobi_3-point_stencil`, `53_stencil_2d_jacobi_5-point_stencil`, `54_stencil_game_of_life`, `46_sparse_la_spmm`, `47_sparse_la_spmv`, `48_sparse_la_sparse_axpy`, `49_sparse_la_sparse_lu_decomp`, `10`–`14_geometry_*`, `00`/`01`/`02`/`04_dense_la_*`, `34_scan_largest_contiguous_subarray_sum`, `40_sort_sort_an_array_of_complex_numbers_by_magnitude`, `24_histogram_count_quartile`, `19_graph_shortest_path`, `26_reduce_product_of_inverses`. No deviation to report.
2. **The "nine quartile definitions" hypothesis for `24` was the wrong axis entirely.** The briefing flagged it as a hypothesis, correctly. The benchmark does not compute statistical quartiles at all: it bins *fractional parts* into four sub-intervals of the unit interval. The Hyndman-Fan readings were enumerated and executed anyway, purely to prove they are excluded. The operative convention axis turned out to be the treatment of negative values and the `(int)` cast — and on that axis the oracle matches **no** reading of the prompt.
3. **The depth staffing was wrong in two directions.** `02_dense_la_gemm` and `04_dense_la_gemv` were correctly classed as mathematically unique for the *arithmetic*, but both carry genuine representational freedom (layout, write semantics) that had to be enumerated and separated — the auditors did so and said why. Conversely `51_stencil_edge_kernel` was staffed as convention-bearing, and the enumeration found 12 candidate conventions, but the prompt turns out to pin every one of them explicitly (kernel matrix, zero padding, clipping, row-major); the enumeration still earned its keep by *proving* the oracle sits on the pinned convention rather than assuming it.
4. **"Convention-sensitive" was a good filter but not a complete one.** The largest single mechanism found is not a convention question at all: it is validators accepting demonstrably wrong answers (NaN acceptance, unenforced boundary windows, vacuous small sizes). That mechanism cuts across the convention-bearing and the mathematically-unique benchmarks alike.
5. **The expectation that this scope would contain `fft/07`-style oracle bugs was not borne out: zero class-C findings.** Every oracle here implements *a* plausible reading of its claimed operation. That is a real result and it bounds the blast radius of the `07` defect.
